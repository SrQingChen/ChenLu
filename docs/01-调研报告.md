## 一、Shizuku：前置依赖与权限提升机制

### 1.1 原理：它是"把 ADB 权限代理给普通 App"的 Binder 中间人

- 用户通过**无线调试配对（Android 11+，免电脑）**、USB ADB 或 root 执行一次启动脚本，在设备上以 `app_process` 拉起 Shizuku server 进程，运行身份为 **shell 用户（uid 2000，ADB 方式）** 或 root。
- 集成了 Shizuku API 的 App 通过 ContentProvider（`ShizukuProvider`，由 `INTERACT_ACROSS_USERS_FULL` 保护）拿到 server 的 IBinder，随后 `App --binder--> Shizuku server --binder--> system_server` 直调特权 API。
- 官方定位：*"be a middle man to receive requests from the app, sent them to the system server, and send back the results"*。
- 来源：<https://shizuku.rikka.app/zh-hans/introduction.html>、<https://github.com/RikkaApps/Shizuku>、<https://github.com/RikkaApps/Shizuku-API/blob/master/README.md>

**为什么比 root 安全（本项目立身之本）**：
- 权限仅为 **shell 级**——以系统 Shell 包 Manifest 声明的权限为边界，**不能读取其他应用 /data 私有数据**，没有 su；
- 授权体系与运行时权限同形：用户在 Shizuku App 内逐 App 批准、**随时可撤销**；
- **无需解锁 bootloader / 刷机 / 改系统分区**，出厂状态即可使用。

### 1.3 App 集成要点（已核实官方 demo）

```kotlin
// 1) build.gradle.kts

```

```xml
<!-- 2) AndroidManifest.xml -->
<provider
    android:name="rikka.shizuku.ShizukuProvider"
    android:authorities="${applicationId}.shizuku"
    android:multiprocess="false" android:enabled="true" android:exported="true"
    android:permission="android.permission.INTERACT_ACROSS_USERS_FULL" />
```

```kotlin
// 3) 状态监听 + 权限三段式（binder 不存活时调用会抛 IllegalStateException）
Shizuku.addBinderReceivedListenerSticky { /* binder 就绪后再调用 */ }
Shizuku.addBinderDeadListener { /* 引导用户打开 Shizuku App 重新启动 */ }
Shizuku.addRequestPermissionResultListener { reqCode, result -> /* ... */ }

if (Shizuku.checkSelfPermission() == PackageManager.PERMISSION_GRANTED) { /* OK */ }
else Shizuku.requestPermission(REQUEST_CODE)
```

**UserService（AIDL）机制**——"用 Shizuku 做高速点击"的核心：App 把自己的 Service 类上传到 Shizuku server 侧，以 shell/root 身份在新进程运行；`destroy()` 是保留事务码 16777114，`unbind` 后需自行清理并 `System.exit()`。UserService 进程**不受非 SDK 接口限制**，可直接调用隐藏 API（如 `InputManager`）。绑定用 `Shizuku.bindUserService(UserServiceArgs(componentName).version(...), connection)`，需 API ≥ 10，建议显式设置 `tag` 防混淆失效。
来源：<https://github.com/RikkaApps/Shizuku-API/blob/master/demo/src/main/java/rikka/shizuku/demo/DemoActivity.java>

### 1.4 用 Shizuku 注入点击：两种方式的性能天壤之别

| 方式 | 单次开销 | 实际频率 | 说明 |
|---|---|---|---|
| a) shell 命令 `input tap x y` | 每次 fork ART 进程，设备内数十 ms～数百 ms | ~10–20 次/秒 | 实现一行代码，但快不起来、耗电 |
| b) **UserService 内直接 `InputManager.injectInputEvent(MotionEvent)`** | 亚毫秒～毫秒级（进程内调用 + InputDispatcher） | **数百 Hz 量级**（工程估计，需自测基准） | 与系统 `input` 命令同一条特权注入路径，shell 身份持有 `INJECT_EVENTS`；无进程创建开销 |

方式 b 代码要点（运行于 UserService 内）：

```java
InputManager im = InputManager.getInstance();
long now = SystemClock.uptimeMillis();
MotionEvent down = MotionEvent.obtain(now, now, MotionEvent.ACTION_DOWN,
        x, y, 1f, 1f, 0, 1f, 1f, 0, 0, InputDevice.SOURCE_TOUCHSCREEN);
im.injectInputEvent(down, 2 /* WAIT_FOR_FINISH */);
// 间隔后注入 ACTION_UP 构成完整点击；swipe 用 ACTION_MOVE 序列
```

来源：AOSP input 命令实现原理；网易易盾《Android 模拟点击研究》（<https://dun.163.com/news/p/561f6e8e3dfb49cc867dded5b6885e1a>，指出 `injectInputEvent` 在 native 层校验注入方 PID/UID，仅 system/shell 可注入）。

### 1.5 激活、限制与 HyperOS 注意点

- **激活方式**：无线调试配对（Android 11+，免电脑，配对仅一次）/ USB ADB / root（唯一支持开机自启）。
- **小米 HyperOS 注意**：需单独开启「USB 调试（安全设置）」；MIUI/POCO 配对码输入可能立即失败（通知样式需切"原生样式"）；锁屏后 Shizuku 可能被停止（社区反馈）。
- **重启失效**：非 root 方式每次重启需重新启动 Shizuku server。**第三方 App 无法直接拉起 Shizuku server**（StarterActivity 未导出，已核实 Manifest），只能检测 binder 死亡后引导用户打开 Shizuku App（配对凭据已保存，打开后一键启动）。v13.6.0 起 Android 13+ 受信任 WLAN 场景可自动启动。
- **替代品**：Dhizuku（共享 Device Owner 权限，与 Shizuku 互补）、Sui（root 用户的 Magisk 模块，提供**与 Shizuku 完全相同的 API**——一套代码同时覆盖 root 与非 root 用户）。

### 1.6 Shizuku 路线 vs 无障碍路线（关键决策依据）

| 维度 | Shizuku（UserService + injectInputEvent） | 无障碍（dispatchGesture） |
|---|---|---|
| 权限门槛 | 一次性 ADB 配对激活 | 开启无障碍即用（更零门槛） |
| 点击频率 | 数百 Hz 量级（估） | 实测稳定 **10–50 次/秒** |
| 界面感知 | 无内置（需自研截图/OCR） | 有 AccessibilityNodeInfo 控件树 |
| 厂商限制 | 不注册无障碍，**不受"受限设置/限制无障碍"影响** | Android 13+ 侧载 App 受 restricted settings 挡；HyperOS 常被自动关闭 |
| 游戏反作弊 | 不出现在无障碍服务列表，事件与 shell input 同源 | 无障碍开启状态可被枚举，游戏风控高发 |
| 重启持久性 | 非 root 重启需重新启动 Shizuku | 一般保持开启 |

**结论：双引擎互补，尘露以"无障碍保底 + Shizuku 增强"分层设计。**

## 二、澎湃 OS 3 超级岛：官方 API、白名单的真实执行与 MAA 案例复盘

### 2.1 已确认的事实（信源：小米开发者平台官方文档 dev.mi.com，共 8 篇「小米超级岛」系列）

- 超级岛是澎湃 OS 3（2025-08 发布，Xiaomi 17 系列首发）的焦点通知能力升级：岛摘要态/展开态、三岛并存、下拉小窗、拖拽分享。**不挑机型只看系统版本**（OS3 = 超级岛；OS2 = 焦点通知），截至 2026-01 已覆盖 52+ 机型，小米 15/16/17 系列与多款平板在列。
- **官方 API 已对第三方开放**，两种接入方式：
  1. **客户端接入**：原生 `Notification` 的 extras 塞 key **`miui.focus.param`**（JSON ≤3072 字节，`param_v2` 结构含 `param_island`（岛数据）、`baseInfo`、`aodTitle` 等字段），系统据此以岛样式渲染；
  2. **MiPush 接入**：推送通道下发，无需进程保活。
- 能力检测：`Settings.System.getInt(resolver, "notification_focus_protocol", 0)` 返回 3 = 支持 OS3 岛。
- 系统预置 22 套场景模板（打车/外卖/支付/文件传输/抢票/导航等），不支持自定义拼装。

来源：<https://dev.mi.com/xiaomihyperos/documentation/detail?pId=2131>（开发指南）、`?pId=2140`（业务介绍）、`?pId=2146>（Q&A）。

### 2.2 官方审核口径与系统侧真实执行（2026-09 复核）

**官方口径**（pId=2132）：开发者认证 → 场景预审+方案审核 → 白名单联调（按 OAID，每应用 ≤10 台、30 天有效）→ 灰度 7–15 天；"未经审核的场景上线，会导致应用的小米超级岛服务停用"。决定性反证原文：**"添加到白名单中的设备，不做本地构建超级岛权限的校验"**——说明客户端 extras 路径存在系统侧校验，白名单设备只是被豁免。`business` 字段官方定义为"运营场景（数据统计）"，不是渲染校验点；**校验的是应用包名白名单**。

**系统侧双层校验（社区多源互证，强证据）**：
- `com.xiaomi.xmsf`（小米服务框架）负责云控白名单**在线校验——且是 fail-open**：云端结果拿不到（断网，-400）时放行渲染，联网查到不在名单（-200）时摘岛；
- MiuiSystemUI 负责最终渲染判断（本地拦截，Xposed 可移除）。
- 旁证：专为"移除焦点通知白名单"而存在的 Xposed 模块生态（HyperFocus，hook 作用域 `com.android.systemui`；HyperCeiler 的"移除焦点通知白名单"开关；1812z/HyperIsland 等），以及 HyperNotification 库 README 明言"澎湃 OS 对于焦点通知有白名单应用限制"。
- **实际表现**：国行 HyperOS 2/3 联网时，非白名单应用的 extras 通知大概率退化为普通通知（不上岛）；部分国际版 ROM 云控覆盖不全、或 xmsf 失联时 fail-open 放行——这是"有人直发 extras 就能上岛"的真相（HyperBridge 382★、Google Play 在架即此机制先例）。

**时长限制的真相**："单次服务 ≤12 小时"与"禁止长期常驻"是**审核口径**而非渲染层硬编码——`timeout` 默认 720 分钟、`islandTimeout` 默认 3600s 都是可设参数（MAA-Meow 设 86400s=24 小时并以 updatable 持续刷新）。"常驻"在技术上可行，被禁的是"未过审的常驻"。

### 2.3 反例复盘：MAA 为什么能常驻上岛 + 尘露的四条通道

**发岛的不是官方 MAA**（官方仓库 MaaAssistantArknights 及 MFAAvalonia 均无此功能，已源码级排除），而是生态内安卓原生客户端 **MAA-Meow**（Aliothmoon，Kotlin+Compose，本身依赖 Shizuku/Root 运行；v0.20.1-beta.3 引入，PR #216）。它**未申请任何小米审核**，原理分两步：

1. 用开源库 HyperNotification（`com.xzakota.hyper.notification:focus-api:1.4`，Maven Central）构建 V3 超级岛 JSON（extras key `miui.focus.param`，外层仍是 `param_v2`），business 冒用官方 **download_progress（下载进度）模板**，大小岛/胶囊进度环/AOD 全套字段——形态与"任务进度"高度契合；
2. **关键一步（灰色）**：在提权进程内对 `com.xiaomi.xmsf` 断网（三级回退：反射 `setUidFirewallRule` → `cmd connectivity set-package-networking-enabled false` → iptables），令云端鉴权 fail-open 放行上岛；任务结束后恢复、断网状态落盘防遗留。**代价：任务期间全机小米推送断网**（作者为此留了"超级岛兼容模式"开关）。

**可复用的纯客户端细节**（与提权无关，任何 App 均可照抄）：固定通知 id + `updatable=true` + `reopen`；1Hz 节流更新 + 内容指纹去重；`sequence` 毫秒递增防时钟回拨乱序；独立 `IMPORTANCE_HIGH` 无声通道（通知级 `setSilent()` 会压掉浮出）；`islandTimeout=86400s`；能力检测（`notification_focus_protocol ≥ 3` / 岛硬件特性 / 用户"焦点通知"开关）不满足自动回退。来源：[MAA-Meow](https://github.com/Aliothmoon/MAA-Meow)、[HyperNotification](https://github.com/xzakota/HyperNotification)、[HyperBridge Issue #256（xmsf fail-open 披露）](https://github.com/D4vidDf/HyperBridge/issues/256)。

**尘露的四条原生岛通道**：

| 通道 | 合规性 | 稳定性 | 尘露定位 |
|---|---|---|---|
| ① 媒体通知自动上岛（MediaSession + MediaStyle；官方 pId=2161："接入媒体通知能力后，将自动上岛"） | ✅ 官方明确**免审核**、无需通知权限 | 高 | 次选（合规原生形态）：title=任务名、subtitle=状态、进度条=任务进度、播放/暂停=连点启停——Focus 不可用或兼容模式关闭时使用 |
| ② extras 直发 `miui.focus.param`（不提权） | 灰色 | 低（国行联网大概率退化普通通知） | 检测到可用（fail-open/国际版）则顺手展示，不依赖 |
| ③ extras + Shizuku 临时断 xmsf（MAA-Meow 式） | 灰色（有 Google Play 在架先例 HyperBridge） | 中（依赖 fail-open 不被修补） | **首选（能用就用）**：尘露本就以 Shizuku 为前置，条件优于 MAA-Meow；兼容模式随 Shizuku 就绪默认启用，透明告知+一键关 |
| ④ 官方审核通道（"任务进度"场景申请） | ✅ | 高（过审后） | 可试不依赖：个人开发者认证 1–3 工作日，但连点器题材过审概率低、灰度周期长 |

**兜底层为传统通知栏**（常驻通知 + Action 按钮，简单可靠、零额外权限）；自绘「尘露岛」胶囊（TYPE_APPLICATION_OVERLAY）降为**后期可选视觉增强**，不进默认链路。注意自绘岛**无法**与系统岛完全一致：系统岛由 SystemUI 在摄像头区域渲染，锁屏/AOD/安全屏幕（FLAG_SECURE）下自绘浮层不可见或被禁，自绘只能覆盖"前台应用上方"这一形态。

### 2.4 HyperOS 后台存活（所有竞品的差评重灾区）

社区共识"三件套"：**省电策略设"无限制" + 关闭应用启动管理（手动开自启动/关联启动/后台活动）+ 最近任务锁定后台**。尘露需内置图形化引导页逐项带跳转；前台服务声明正确 `foregroundServiceType`；被杀后 JobScheduler/定时器均失效，不可依赖。

### 3.2 用户痛点 Top 8（按强度排序）→ 尘露对策

| # | 痛点 | 尘露对策 |
|---|---|---|
| 1 | 广告轰炸 + 会员付费墙（多点/高频常为会员专属） | **完全免费无广告无会员**，开源 |
| 2 | 点击频率上限低（无障碍实测 10–50 次/秒，宣传"1000 次/秒"是话术） | Shizuku 引擎毫秒级注入，实测数据透明展示 |
| 3 | 多点"伪并行"（实为顺序循环） | 明确提供"时序编排"与"单手势多指（≤10 指）同步"两种模式并如实标注 |
| 4 | 后台被杀 / 无障碍被系统关闭（MIUI/HyperOS 重灾区） | FGS + 图形化保活引导三件套 + binder 死亡监听自动降级 |
| 5 | 游戏内失效/被检测（无障碍服务被枚举） | Shizuku 引擎不注册无障碍；回放随机坐标偏移+时序抖动（反作弊文献证实"机械化节奏"是主要识别特征，竞品均未做成卖点） |
| 6 | root 门槛 | 双引擎：无障碍零门槛 + Shizuku 免 root 增强 |
| 7 | 录制能力弱（无智能判断、无多点时序） | Shizuku getevent 真实触摸录制 / API 34 无障碍触摸观察 / 手动可视化编排三档 |
| 8 | UI 丑、操作繁琐 | Compose + Material 3 全新设计，悬浮面板一步到位 |

### 3.3 关键技术事实速查

- `dispatchGesture`：无强制最小间隔，实测 10–50 次/秒；单手势最多 **10 条 stroke（10 指）**、时长上限约 60s；`continueStroke`（API 26+）可拼接长手势。
- `input tap`：300–800ms/次（进程创建是瓶颈）。
- `injectInputEvent`（shell/root）：毫秒级，数百 Hz。
- 无障碍 `takeScreenshot`（API 30+）：系统节流约 **333ms/张（≈3 FPS）**，仅适合低频找色兜底。
- MediaProjection + ImageReader：10–30ms 级延迟，实时取色首选；Android 14+ 每次会话需用户确认 + `mediaProjection` 类型前台服务，顺序错即 SecurityException。
- **Shizuku 连点器赛道目前无成熟高星竞品**（仅 1 个 1★ 新项目用 input tap 实现）——**明确的差异化空白**，尘露以 injectInputEvent 方案直接站上技术制高点。

| Room / DataStore | **2.8.x（或 3.0）/ 1.1.7** | Room KMP stable |
| targetSdk | **36**（Play 2026-08-31 起强制） | 国内商店 ≥34 稳妥，36 一并达标 |
| minSdk | **26（Android 8）** | dispatchGesture 需 24+、takeScreenshot 需 30+、无障碍触摸观察需 34+——按能力分级 gating |

### 4.2 政策红线（工具类 App 逐条）

1. **前台服务**：Android 14+ 必须声明 `foregroundServiceType`（兜底 `specialUse` 需文字说明），缺失即 crash；Android 15 的 `dataSync` 每日累计 6 小时超时；**悬浮窗必须已可见才能借悬浮窗场景启动 FGS**。
2. **悬浮窗**：`Settings.canDrawOverlays()` 检查；MIUI/HyperOS 有独立"显示悬浮窗"开关（默认拒绝）；Android 13+/15 侧载 App 受 restricted settings 收紧。
3. **通知/闹钟**：`POST_NOTIFICATIONS`（33+）运行时权限；精确闹钟 Android 14 起默认拒绝需引导。
4. **MediaProjection**：Android 14+ 每次授权会话需确认 + 先同意再启动 `mediaProjection` FGS；Android 15 屏幕共享常驻 chip 指示条。
5. **无障碍**：`isAccessibilityTool="true"`；侧载 App 需用户手动"允许受限设置"；`takeScreenshot` 约 3 FPS 节流。
6. **预测式返回 / edge-to-edge**：target 36 强制。

### 4.3 Compose 悬浮窗实现要点

- `LifecycleService` + `ComposeView` + `WindowManager.addView(TYPE_APPLICATION_OVERLAY)`；**必须**手动注入 `ViewTreeLifecycleOwner / ViewModelStoreOwner / SavedStateRegistryOwner`，onDestroy 逆序清理，否则崩溃/泄漏。
- 悬浮窗进程若未跑过主 Activity，Compose runtime 与 Baseline Profile 未初始化，首帧卡顿——尘露"先开 App 再开悬浮窗"的流程天然规避。
- 选型：轻控件（准星、拖拽球）用 View 体系更轻；配置面板用 ComposeView。参考：EasyWindow（<https://github.com/getActivity/EasyWindow>）、ComposeOverlayViewService.kt Gist 模板。

- **Smart-AutoClicker / Klick'r**（<https://github.com/Nain57/Smart-AutoClicker>）：图像触发连点器，功能形态参考（GPL-3.0，**只看思路不抄代码**，避免许可证传染争议）。

## 五、调研总结论

1. **Shizuku 完全可行且是最大差异化**：免 root 获 shell 级 `injectInputEvent`，毫秒级高频点击 + 不注册无障碍（规避检测与厂商限制）；赛道空白。工程上以 UserService + AIDL 落地，无 root 生态还有 Sui 自动兼容。
2. **超级岛原生通道分层可行**：③ MAA-Meow 式「Shizuku 临时断 xmsf 令云端鉴权 fail-open」为**首选**——能用就用（兼容模式随 Shizuku 就绪默认启用，透明告知+一键关）；① 媒体通知自动上岛（官方免审核）为次选；传统通知栏兜底；自绘尘露岛降为可选视觉增强，不进默认链路。
3. **无障碍引擎必须保留**作为零门槛默认层，同时提供控件树读取等 Shizuku 给不了的能力；两引擎抽象统一接口。
4. **图色层双通道**：MediaProjection 实时流为主（10–30ms），无障碍 takeScreenshot 为免授权兜底（3 FPS）。
5. **现代基线**：Kotlin 2.4 + Compose BOM 2026.08 + Hilt + Room/DataStore + 模块化（NIA 式），minSdk 26 / targetSdk 36。

## 六、发布与更新分发：GitHub 开源 + Mirror酱（MirrorChyan）

### 6.1 Mirror酱是什么

- **Mirror酱 = MirrorChyan**（<https://mirrorchyan.com>），第三方开源应用更新分发平台：境内 6000+ 阿里云/腾讯云 CDN 节点加速开源应用的版本更新；前后端全部开源（GitHub [MirrorChyan 组织](https://github.com/orgs/MirrorChyan/repositories)，AGPL-3.0）；2025-02 上线，与 MAA 社区深度绑定（MAA v5.13.0 起接入，下载分成反哺社区），现 80+ 应用在架（MAA 系自动化工具为主体，**MAA-Meow 也在架**）。
- **商业模式**：检查更新 API 免费；CDN 下载需用户 CDK 订阅（月 ¥6.9 / 季 ¥12.9 / 年 ¥29.9，**一码通用平台内全部项目**）。开发者接入免费且获下载分成（GPL 允许对分发服务收费，与开源完全兼容）。

### 6.2 接入方式（联系制，非自助）

- 集成 QQ 群 **1026040805** 申请资源 ID（`rid`）与 `upload_token`（自行开启无效）；官方提供 GitHub Action [`MirrorChyan/uploading-action@v1`](https://github.com/MirrorChyan/uploading-action)（MIT）：`filetype: latest-release` 可在发 GitHub Release 时**自动转传**（支持 `os: android`，channel 由 tag 推断 stable/beta/alpha）；官方甚至会为接入项目 PR 定制 CI/CD。模板参考 MaaXYZ/MaaPracticeBoilerplate 的 `mirrorchyan_release.yml`。
- 审核：法律合规初审 **3 个工作日** + 季度复查；禁止赌博/色情/网络攻击工具；要求 OSI 开源许可证（**GPL-3.0 满足**）。游戏自动化类大量在架；无游戏绑定的通用连点器能否过审，接入前入群确认。
- 可用性风险：个人/小团队基建，无硬性 SLA（连续 72 小时不可用才算重大违约，赔偿上限为剩余订阅费 2 倍）→ **必须永远保留 GitHub 主线路**，Mirror酱只做加速层。未搜到跑路/长期宕机/分成违约记录。

### 6.3 客户端更新检查 API（唯一对外接口，无需鉴权）

```
GET https://mirrorchyan.com/api/resources/{rid}/latest
    ?current_version=v1.2.3&cdk=XXX&user_agent=ChenLu
    &os=android&arch=arm64&channel=stable
→ { code, msg, data: { version_name, release_note, url?, sha256?,
                       update_type: incremental|full, cdk_expired_time? } }
```

无 CDK 也返回版本信息（不给 CDN 直链）；官方建议**始终先用本 API 检查更新**（国内连通性好，还支持增量包），拿不到下载链接再回退 GitHub。最佳参考实现：MAA-Meow 的 `MirrorChyanApiClient` + 双源 `UpdateSource` 抽象（AGPL，仅参考思路）；MXU（MFA 系通用更新组件）同构逻辑。

### 6.4 互补渠道结论

- **ghproxy 前缀链**（ghfast.top / gh-proxy.com，2026 年仍运营）：GitHub 直连失败的多前缀轮试兜底，可自建（WJQSERVER-STUDIO/ghproxy）。
- **IzzyOnDroid**：海外 FOSS 合规通道；要求最新 Release 附 APK 且单包 **<30MB** + fastlane 元数据；Shizuku 本体在架（依赖 Shizuku 不构成收录障碍）。F-Droid 官方源构建可复现要求严、周期长，不作主选。
- **Gitee/GitCode**：仅做代码只读镜像（Gitee 2022 起新仓库需人工审核，自动化题材易卡），不做分发主通道。
- **蒲公英/fir.im**：仅封闭内测期扫码分发，公开发布后撤下。
- **应用内自更新合规**：`REQUEST_INSTALL_PACKAGES` 在 Google Play 属受限权限且"绕店自更新"通常被拒，国内商店同样禁止——**侧载开源版保留内置更新器，未来商店版移除**（走商店升级）。

### 6.5 对尘露的结论

GitHub Releases 为唯一事实源与永久免费主线路；Mirror酱为国内加速通道；应用内更新检查顺序：**Mirror酱 API → GitHub releases/latest（+ ghproxy 前缀链）**；下载支持 CDK 直链（可选）与 GitHub 兜底；安装走 FileProvider + ACTION_VIEW 用户确认。README 口径："尘露永远可从 GitHub 免费获取；国内用户可选购买 Mirror酱 CDK 获得 CDN 加速，无 CDK 也能正常检查与更新。"
